\chapter*{Abstract}
\thispagestyle{plain}
In the modern digital era, the massive expansion of unstructured multimedia and binary data presents two paramount engineering challenges: storage bandwidth consumption and information confidentiality. Conventional compression utilities often function as opaque ``black-box'' programs and frequently divorce data reduction from cryptographic authentication. 

This project presents the engineering and implementation of a \textbf{Secure File Compression System} built strictly upon \textbf{Clean Architecture} principles. The system implements a dual-engine architecture featuring lossless \textbf{Huffman Variable-Length Coding} alongside standard \textbf{DEFLATE (RFC 1951 / ZIP Level 9)} compression. The core Huffman engine analyzes byte-frequency distributions, constructs an optimal binary prefix tree via a min-heap priority queue, and packs variable-length codewords into a bitstream with a self-contained header dictionary that guarantees 100\% lossless reconstruction.

To address security, the system incorporates military-grade \textbf{AES-256-CBC} encryption with \textbf{PBKDF2} key derivation (15,000 iterations) and an \textbf{Encrypt-then-MAC (HMAC-SHA256)} authentication paradigm, guarding against chosen-ciphertext and bit-flipping tampering. The system includes an interactive graphical user interface featuring live SVG-rendered Huffman prefix trees, real-time Shannon Entropy calculations, an encrypted vault repository, and a multi-user authentication system backed by bcrypt password hashing. A dual-database persistence layer seamlessly operates on MySQL 8.0 with automatic zero-configuration SQLite fallback.

\chapter{Introduction}

\section{Purpose}
The purpose of the \textbf{Secure File Compression System} is to deliver a transparent, high-performance, and cryptographically verified software application for reducing file storage footprints while guaranteeing absolute data confidentiality. 

Historically, data compression and cryptographic security were managed as disparate tasks: users compressed archives using generic utilities, then manually encrypted them using third-party cryptographic software. This fractured process frequently led to vulnerabilities, such as insecure temporary files, leaked metadata, and vulnerability to padding oracle attacks.

The \textbf{Secure File Compression System} solves these issues by unifying entropy-based data reduction (Huffman Coding), dictionary compression (DEFLATE), and authenticated encryption (AES-256 with HMAC-SHA256) inside a unified, decoupled Clean Architecture. Furthermore, the system provides visual insight into compression theory by dynamically calculating Shannon Entropy and rendering the internal binary prefix tree graph.

\section{Scope}
The scope of this project encompasses:
\begin{enumerate}
    \item \textbf{Lossless Entropy Encoding:} Autonomous Huffman coding capable of processing arbitrary text, source code, documents, and binaries without external dictionary dependencies.
    \item \textbf{Dual Compression Modes:} Real-time comparison between Huffman variable-length encoding and RFC 1951 DEFLATE (ZIP Level 9) compression.
    \item \textbf{Military-Grade Cryptography:} AES-256-CBC authenticated encryption, PBKDF2 (15,000 iterations) key derivation, and HMAC-SHA256 integrity verification.
    \item \textbf{Interactive Educational Visualization:} Interactive SVG rendering of the generated binary prefix tree with bit-branch paths ($0$ and $1$), accompanied by a codebook dictionary and Shannon Entropy metrics.
    \item \textbf{Multi-User Vault \& Access Control:} User authentication with bcrypt password hashing (cost factor 12), user-specific archive vaults, and tamper-resistant activity audit logging.
    \item \textbf{Dual Storage \& Persistence:} Production-grade MySQL relational database persistence with zero-configuration SQLite fallback for immediate local deployment.
\end{enumerate}

\section{Problem in Existing System}
Traditional compression tools and contemporary academic utilities exhibit several notable deficiencies:
\begin{itemize}
    \item \textbf{Black-Box Obscurity:} Most commercial tools (e.g., WinRAR, 7-Zip) execute compression as an opaque background routine, offering no feedback on symbol probability distribution, entropy limits, or tree construction.
    \item \textbf{Unauthenticated Encryption:} Many traditional archive tools use unauthenticated encryption modes (such as standard ZipCrypto or basic AES-CTR), making archives susceptible to bit-flipping attacks and ciphertext alteration.
    \item \textbf{Monolithic Code Tight-Coupling:} Academic software implementations often combine UI rendering, file reading, compression algorithms, and database queries in single unstructured scripts, violating SOLID principles.
    \item \textbf{Rigid Database Dependencies:} Systems that strictly require manual MySQL service configuration fail immediately in portable demonstration environments.
\end{itemize}

The proposed system addresses each of these limitations through clean layered software engineering.

\chapter{System Requirement Analysis}

\section{Information Gathering}
Information gathering for this project was conducted through:
\begin{itemize}
    \item \textbf{Algorithmic Research:} Study of David Huffman's foundational 1952 paper, \textit{``A Method for the Construction of Minimum-Redundancy Codes''}, and Claude Shannon's 1948 mathematical treatise, \textit{``A Mathematical Theory of Communication''}.
    \item \textbf{Cryptographic Standards Analysis:} Review of NIST Special Publication 800-38A (Block Cipher Modes of Operation) and RFC 2898 (PKCS \#5: Password-Based Cryptography Specification).
    \item \textbf{Architectural Review:} Analysis of Robert C. Martin's \textit{Clean Architecture} paradigms regarding boundary enforcement, Dependency Inversion, and entity isolation.
\end{itemize}

\section{Determination of System Requirements}

\subsection{Why Such a System is Required?}
The system is required to solve the twin challenges of data volume explosion and cyber tampering through a verifiable, open, and educational software platform. It enables users to observe compression mechanisms at the bit level while applying military-grade confidentiality before files are stored or transmitted.

\subsection{Problems in Previous Implementations}
Previous academic prototypes suffered from:
\begin{itemize}
    \item Inability to decompress autonomously due to unpersisted Huffman tree tables.
    \item Vulnerability to memory overflow when encoding files larger than a few kilobytes.
    \item Absence of user authentication and audit logging.
\end{itemize}

\subsection{Hardware Requirements}
\begin{itemize}
    \item \textbf{Processor:} Modern x86-64 / AMD64 dual-core processor (Intel Core i3 / AMD Ryzen 3 or higher).
    \item \textbf{RAM:} Minimum 512 MB (2 GB recommended for multi-megabyte file chunking).
    \item \textbf{Hard Disk:} Minimum 100 MB free space for application storage, runtimes, and file vaults.
    \item \textbf{Display:} Minimum $1024 \times 768$ resolution with color support for SVG tree visualization.
\end{itemize}

\subsection{Software Requirements}
\begin{itemize}
    \item \textbf{Operating System:} Windows 10 / 11, Linux (Ubuntu/Debian), or macOS.
    \item \textbf{Runtime Environment:} PHP 8.2 or 8.3 with \texttt{OpenSSL}, \texttt{Zip}, \texttt{PDO}, \texttt{pdo\_mysql}, and \texttt{pdo\_sqlite} extensions enabled.
    \item \textbf{Database System:} MySQL 5.7+ / 8.0+ or MariaDB; automatic fallback to SQLite 3.
    \item \textbf{Web Browser:} Modern HTML5 browser supporting SVG and ES6 JavaScript (Google Chrome, Mozilla Firefox, Microsoft Edge).
    \item \textbf{Web Server:} Built-in PHP development server (\texttt{php -S}) or Apache 2.4.
\end{itemize}

\subsection{Implementation Languages \& Technologies}
\begin{itemize}
    \item \textbf{Front-End:} HTML5, Vanilla CSS3 (Custom Obsidian Glassmorphism design tokens), Vanilla JavaScript (ES6+ Fetch API, DOM manipulation).
    \item \textbf{Back-End Core:} Pure PHP 8.3 with strict typing (\texttt{declare(strict\_types=1)}), Object-Oriented Clean Architecture.
    \item \textbf{Data Access:} PHP Data Objects (PDO) with parameterized prepared statements.
\end{itemize}

\section{System Feasibility}

\subsection{Technical Feasibility}
The required technologies (PHP 8.3, OpenSSL, WebCrypto API, PDO, and modern browsers) are open-source, widely adopted, and available without licensing fees. The priority queue min-heap algorithm operates with $O(N \log K)$ computational complexity (where $N$ is file size and $K$ is alphabet size $\le 256$), ensuring low CPU overhead. The project is technically feasible.

\subsection{Operational Feasibility}
The system features a streamlined web UI with intuitive drag-and-drop dropzones, real-time password strength indicators, 1-click demo login credentials, and clear result metrics. Users require no specialized training to compress, encrypt, or restore files. Operational feasibility is established.

\subsection{Economic Feasibility}
The system is constructed using 100\% free, open-source technologies with zero software licensing costs. Minimal hardware requirements permit deployment on existing commodity hardware. Economic feasibility is confirmed.

\chapter{System Design \& Architecture}

\section{Clean Architecture Layering}
The system strictly enforces the four concentric layers of Clean Architecture:
\begin{enumerate}
    \item \textbf{Domain Layer (Enterprise Business Rules):} Contains core entities (\texttt{HuffmanNode}, \texttt{FileRecord}, \texttt{ActivityLog}, \texttt{User}) with zero external framework dependencies.
    \item \textbf{Interfaces / Contracts Layer:} Declares abstract behavioral contracts (\texttt{CompressionInterface}, \texttt{EncryptionInterface}, \texttt{FileRepositoryInterface}, \texttt{UserRepositoryInterface}) using Dependency Inversion.
    \item \textbf{Services Layer (Application Business Logic):} Contains concrete implementations (\texttt{HuffmanEngine}, \texttt{ZipEngine}, \texttt{AesEncryptionService}, \texttt{FileStorageService}, \texttt{AuthService}).
    \item \textbf{Controllers / Interface Adapters:} Translates HTTP and JSON payloads into service calls (\texttt{CompressionController}, \texttt{FileController}, \texttt{AuthController}).
    \item \textbf{Infrastructure Layer:} Implements persistence drivers (\texttt{DatabaseFileRepository}, \texttt{DatabaseUserRepository}) interfacing with MySQL and SQLite through PDO.
\end{enumerate}

\chapter{Algorithm \& Mathematical Analysis}

\section{Information Theory \& Shannon Entropy}
Claude Shannon defined the theoretical lower bound for lossless compression in 1948. For an alphabet $\mathcal{S} = \{s_1, s_2, \dots, s_K\}$ with occurrence probabilities $P(s_i)$, the \textbf{Shannon Entropy} $H(X)$ is formulated as:
\begin{equation}
    H(X) = - \sum_{i=1}^{K} P(s_i) \log_2 P(s_i) \quad \text{(bits per symbol)}
\end{equation}

Shannon's Source Coding Theorem establishes that no lossless compression algorithm can represent data with fewer average bits than $H(X)$. 

Given an alphabet codebook with codeword lengths $l_i = \text{length}(\text{code}(s_i))$, the average codeword length $L_{\text{avg}}$ is:
\begin{equation}
    L_{\text{avg}} = \sum_{i=1}^{K} P(s_i) \cdot l_i
\end{equation}

The theoretical \textbf{Coding Efficiency} $\eta$ is measured as:
\begin{equation}
    \eta = \frac{H(X)}{L_{\text{avg}}} \times 100\%
\end{equation}

\section{Huffman Coding Engine Implementation}
Huffman coding constructs an optimal prefix tree (where no codeword is a prefix of any other, enabling unambiguous continuous streaming).

\subsection{Algorithmic Steps}
\begin{enumerate}
    \item \textbf{Scan \& Frequency Map:} Read byte sequence of length $N$. Tally occurrences $f(b)$ for every distinct byte $b \in [0, 255]$.
    \item \textbf{Priority Queue Initialization:} Insert all symbols into a min-priority queue where priority is frequency $f(b)$.
    \item \textbf{Tree Construction:} Repeatedly extract the two minimum nodes $n_1$ and $n_2$. Form a parent internal node $n_p$ with frequency $f(n_p) = f(n_1) + f(n_2)$ and children $n_{\text{left}} = n_1$, $n_{\text{right}} = n_2$. Insert $n_p$ back into the queue. Repeat until one root node remains.
    \item \textbf{Prefix Code Assignment:} Traverse from root to leaves. Append \texttt{'0'} when branching left and \texttt{'1'} when branching right.
    \item \textbf{Bit Packing:} Transform the variable bitstrings into 8-bit unsigned integers via bitwise shift operations ($(\text{buffer} \ll 1) \mid \text{bit}$).
\end{enumerate}

\subsection{Why Pre-Compressed Files (PDF, JPG) Expand: The Entropy Limit}
When compressing structured uncompressed files (\texttt{.txt}, \texttt{.csv}, \texttt{.json}, source code), symbol frequencies are non-uniform (e.g., spaces and vowels dominate), producing high compression savings ($30\%\text{--}60\%$).

Conversely, modern formats like \textbf{PDF, JPEG, and ZIP} are already pre-compressed using internal Deflate/DCT encoders. In these formats, byte distributions approach uniform randomness, meaning:
\begin{equation}
    P(s_i) \approx \frac{1}{256} \implies H(X) \approx \log_2(256) = 8.0 \text{ bits/byte}
\end{equation}
When entropy reaches 8 bits per byte, Huffman coding cannot assign codes shorter than 8 bits without violating Kraft's inequality. Furthermore, our autonomous archive format stores a \textbf{frequency table header} ($\approx 1.2\text{ KB}$ for 256 symbols) so that decompression can operate without external codebooks. 
Adding this necessary header overhead to an already maximally-compressed payload results in a small negative ratio (e.g., $-4.15\%$). This behavior confirms the \textbf{Pigeonhole Principle} of computer science: no lossless compression algorithm can compress all possible input bitstrings.

\section{AES-256 Authenticated Encryption}
To ensure security, the system implements the \textbf{Encrypt-then-MAC (EtM)} architecture.
\begin{enumerate}
    \item \textbf{Key Derivation:} Given passphrase $K_{\text{pass}}$ and a cryptographically random 16-byte salt, PBKDF2 generates a 64-byte derived key:
    \begin{equation}
        K_{\text{derived}} = \text{PBKDF2-HMAC-SHA256}(K_{\text{pass}}, \text{salt}, 15000, 64)
    \end{equation}
    The first 32 bytes constitute the encryption key $K_{\text{enc}}$, and the remaining 32 bytes form the MAC authentication key $K_{\text{mac}}$.
    \item \textbf{AES-256-CBC Encryption:} Plaintext bitstream $P$ is encrypted with random 16-byte initialization vector (IV):
    \begin{equation}
        C = \text{AES-256-CBC}(P, K_{\text{enc}}, \text{IV})
    \end{equation}
    \item \textbf{HMAC Authentication:} An authentication signature $T$ is computed over the entire container:
    \begin{equation}
        T = \text{HMAC-SHA256}(K_{\text{mac}}, \text{salt} \parallel \text{IV} \parallel C)
    \end{equation}
    During decryption, timing-safe equality comparison ($\text{hash\_equals}$) validates $T$ prior to cipher execution, preventing chosen-ciphertext and bit-flipping attacks.
\end{enumerate}

\chapter{Conclusion \& Future Scope}

\section{Conclusion}
The \textbf{Secure File Compression System} successfully demonstrates that entropy-based data reduction and military-grade authenticated encryption can be integrated inside a modular, decoupled Clean Architecture. The project meets all academic objectives:
\begin{itemize}
    \item Implemented lossless Huffman coding with min-heap construction and self-contained header reconstruction.
    \item Enforced AES-256-CBC encryption with PBKDF2 key derivation and HMAC-SHA256 authentication.
    \item Delivered an educational interface with interactive SVG prefix trees, codebook tables, and Shannon Entropy calculations.
    \item Provided a dual-database persistence system (MySQL/SQLite) and user authentication with bcrypt password hashing.
\end{itemize}

\section{Future Scope}
Future enhancements planned for the platform include:
\begin{itemize}
    \item \textbf{Adaptive Huffman Coding (Vitter Algorithm):} Implementing one-pass dynamic tree adjustment to eliminate header frequency table overhead on small files.
    \item \textbf{Parallel Multi-Threaded Chunking:} Utilizing Web Workers on the frontend and worker threads in PHP for multi-gigabyte file compression.
    \item \textbf{Public Key Infrastructure (RSA / ECC):} Allowing users to compress and encrypt archives with a recipient's public key for zero-shared-secret communication.
\end{itemize}
